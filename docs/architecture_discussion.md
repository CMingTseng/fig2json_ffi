# Fig2Json 技術架構與 GUI 選型討論紀錄

本文件紀錄了關於 `fig2json` 工具未來發展的技術選型討論，涵蓋 GUI 框架選擇、跨語言架構調整以及轉換邏輯優化的方向。

---

## 1. GUI 框架選型 (Rust vs. Go)

針對現有的 Rust 核心邏輯，探討了若要實作圖形化界面 (GUI) 的不同路徑：

### Rust 方案
*   **Tauri (推薦)**: 
    *   **架構**: 前端 HTML/CSS/JS + 後端 Rust。
    *   **優點**: 界面美觀、開發生態豐富、打包體積小。適合需要「設計感」的工具。
*   **egui**: 
    *   **架構**: 純 Rust (Immediate mode)。
    *   **優點**: 開發速度極快、無 JS 依賴。適合工程師自用的內部工具。
*   **Slint**: 專注於效能與專業外觀，適合嵌入式或高性能桌面應用。

### Go 方案 (若考慮遷移)
*   **Wails (對標 Tauri)**: 
    *   **架構**: 前端 Web + 後端 Go。
    *   **優點**: Go 與 JS 之間的通訊極其簡便，開發效率高。
*   **Fyne**: 純 Go 界面，支援跨平台（含行動端），開發體驗好但界面靈活性較低。

**結論**: 由於核心邏輯已由 Rust 實作，**Tauri** 是目前損失最小且產出品質最高的選擇。

## 2. 轉換邏輯與混合架構探討 (Rust + WASM + JS)

針對「轉換邏輯」是否應遷移至 JavaScript (QuickJS) 的深入討論：

### 核心考量：效能與靈活性
*   **Rust 的優勢**: 處理超大型檔案（如 100MB+）時，二進制解析 (Kiwi) 與深層樹狀結構處理的效能與記憶體安全性極佳。
*   **JS/QuickJS 的優勢**: 轉換邏輯（如欄位過濾、屬性對齊）變動頻繁，JS 的動態性更適合頻繁微調，且前端開發者參與門檻低。

### 建議架構：Hybrid "Core in Rust, Logic in JS"
為了兼顧效能與靈活性，建議採用以下折衷架構：

1.  **Rust (WASM 層)**:
    *   負責 **Heavy Lifting**: ZIP 解壓、Kiwi 二進制解碼、圖片處理、初步大型結構建立。
    *   將結果編譯為 WebAssembly (WASM)。
2.  **JavaScript (邏輯層)**:
    *   負責 **Transformation**: 執行遞歸遍歷、欄位過濾、CSS 屬性轉換。
    *   這部分邏輯可以運行於 QuickJS (CLI)、Browser (Tauri/Web)、或是 Figma Plugin 環境中。

### 混合架構的優點
*   **邏輯複用**: 一套轉換邏輯 (JS) 可以同時跑在桌面工具、Web 預覽頁面以及 Figma 插件中。
*   **熱更新**: 無需重新編譯整個 Rust 項目即可調整過濾規則。
*   **生態對接**: 完美契合 Figma 插件以 JS 為主的生態系統。

## 3. 下一步行動建議
*   **第一階段**: 繼續優化 Rust 核心的解析效能，確保能穩定處理大型 `.fig` 檔案。
*   **第二階段**: 嘗試將現有的 `src/schema/transformations/*.rs` 邏輯部分抽象化，評估將其遷移至 JS 執行環境的可行性。
*   **第三階段**: 使用 **Tauri** 建立桌面版客戶端，將 WASM 核心與 JS 轉換邏輯整合。
